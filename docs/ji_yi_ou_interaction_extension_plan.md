# 季一藕「带美食拜访」互动：现状支持度与可扩展方案

## 1. 结论先行

你提出的核心玩法（带不同美食给季一藕、按类型掉落不同奖励、可能随机获得八卦/医理文本）在当前项目中**已具备基础实现**，而且奖励数值与文案已经基本对齐。

但从后续迭代角度看，目前实现是“**季一藕专用、逻辑分散、主要靠硬编码**”的结构。若未来要扩展到更多 NPC、多套赠礼规则、概率权重、条件解锁与运营配置，会遇到维护成本上升问题。

---

## 2. 目前已支持（对应你这次需求）

### 2.1 赠礼品类识别已支持

- 已支持糖葫芦、小笼包、各式糕点、其他干果零食四类识别。
- 其中糖葫芦和小笼包按固定 `item.id` 精确识别；糕点按关键词；其余 `snack_` 前缀归类为干果零食。

### 2.2 奖励效果已支持，且与需求基本一致

- 糖葫芦：经验 +30、体力 +10、金钱 +30，并赠送“怎样的饮食才算健康的唠嗑”“平安脉”。
- 小笼包：经验 +30、金钱 +30，并赠送“当下节气养生的相关事宜”和 2 株仙鹤草。
- 各式糕点：经验 +20、体力 +20、金钱 +20，并赠送“语重心长的教诲”“艾灸体验”。
- 其他干果零食：体力 +50，并赠送“针灸体验”和 1 株仙鹤草。

### 2.3 “随机掉落八卦/医学常识”已支持

- 赠礼后会进行一次随机掉落判定（当前约 30% 概率触发文本）。
- 文本池分为八卦池与医理池，二选一后随机抽条目。

### 2.4 交互入口与流程已支持

- NPC 列表中，季一藕点击“送礼”会打开专属美食选择弹窗。
- 玩家确认后执行赠礼：扣除礼物、应用奖励、写入日志文本。

### 2.5 奖励道具词条已支持

- 你描述的“唠嗑、平安脉、节气养生、教诲、艾灸体验、针灸体验、仙鹤草”均已在道具数据中存在。

## 3. 目前不支持 / 支持不足（面向扩展）

### 3.1 仅支持季一藕单 NPC 的定制逻辑

- 现在规则函数命名与调用路径都绑定 `JiYiOu`，不具备通用化配置能力。
- 若新增“其他 NPC 也有按礼物分类奖励”，会复制粘贴较多逻辑。

### 3.2 配置分散、缺少统一数据驱动层

- 交互分类、奖励效果、Lore 文本池、UI 分类顺序分散在多个位置（数据层、组件层、store 层）。
- 未来策划改数值/改文案时，需要跨文件修改，容易漏改。

### 3.3 随机掉落机制可调参数不足

- 掉落概率和池选择概率写死在函数中，暂不支持按 NPC、好感度、节气、任务状态动态调整。

### 3.4 规则匹配能力有限

- 目前品类匹配主要依赖 `item.id` 与名称关键词，缺少“标签化规则”（如 `tags: ['pastry','festival']`）与优先级机制。
- 当道具规模继续扩大时，关键词冲突会增加维护成本。

### 3.5 缺少规则验证工具

- 暂无针对“礼物 -> 分类 -> 奖励”的自动校验与冲突检查（例如奖励里引用了不存在的 `item.id`）。

## 4. 新增模块计划（可扩展版本）

> 目标：把“某 NPC 收到某类礼物后触发某奖励+随机文本”抽象成通用能力，季一藕是第一套配置。

## 阶段 A：引入通用赠礼规则模块（最小可用）

### A1. 新增配置文件

- 建议新增：`src/data/npcGiftInteractionRules.ts`
- 用统一 schema 声明：
  - `npcId`
  - `giftMatchers`（按 id / 前缀 / 标签 / 关键词 / 自定义函数）
  - `rewardByCategory`
  - `loreDrop`（概率、文本池、权重）
  - `uiHints`（分类展示名、顺序、说明文案）

### A2. 新增规则引擎

- 建议新增：`src/services/npcGiftInteractionEngine.ts`
- 对外统一 API：
  - `getGiftCandidates(npcId, inventory)`
  - `resolveGiftCategory(npcId, item)`
  - `buildGiftOutcome(npcId, item, state)`

### A3. store 接口泛化

- 当前 `giftFoodToJiYiOu` 可演进为 `giftItemToNpc(npcId, itemId)`。
- `giftFoodToJiYiOu` 可保留为兼容壳函数（内部转调新接口），避免一次性改太多调用点。

## 阶段 B：UI 与文案解耦

### B1. 通用化赠礼弹窗

- 将 `NPCGiftModal` 从“季一藕专属分类”改为“按 `npcId` 拉取规则”展示。
- 分类排序与说明文案从规则读取，避免组件内硬编码。

### B2. 回执模板化

- 增加 `messageTemplate`，支持类似：
  - `你把{itemName}递给{npcName}，{rewardText}{loreText}`
- 后续可接入多语言或活动皮肤文案。

## 阶段 C：验证与运营能力

### C1. 开发期规则校验

- 启动时校验：
  - 配置中 `itemId` 是否存在
  - 分类是否重复/未覆盖
  - 概率区间是否合法

### C2. 调试面板（可选）

- 在开发页增加“赠礼模拟器”：指定 NPC、物品，预览分类命中与奖励结果，方便策划验收。

### C3. 事件系统联动（可选）

- 将 `loreDrop` 升级为“可触发事件 ID 列表”，支持复杂分支（好感度门槛、一次性剧情、成就触发）。

---

## 5. 推荐落地优先级

1. **先做 A（数据与引擎）**：解决扩展性根问题。
2. **再做 B1（弹窗通用化）**：确保前台可复用。
3. **补 C1（配置校验）**：降低线上配置风险。
4. 其余 B2/C2/C3 按迭代节奏增量推进。

---

## 6. 对你这次需求的建议

- 若目标只是“上线季一藕这一套玩法”，当前代码已经可用，只需做少量文案/数值微调。
- 若你计划后续给多个 NPC 追加类似玩法，建议直接按本计划做一次通用模块改造，避免后面返工。
